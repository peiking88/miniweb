## 第一章 关键字规则

### 1.1 存储类型关键字

#### auto
- 声明自动变量，缺省时编译器一般默认为 auto
- 现代编译器中 auto 关键字基本不再使用

#### register
- 请求编译器尽可能将变量存在 CPU 内部寄存器中而不是通过内存寻址访问
- 寄存器速度非常快，但数量有限（通常几个到几十个）
- **使用限制**：
  - register 变量必须是能被 CPU 寄存器所接受的类型
  - 必须是单个值，长度应小于或等于整型长度
  - 不能用 & 获取 register 变量的地址（因为不在内存中）
  - 只有局部自动变量和形式参数可以作为 register 变量
  - 局部静态变量不能定义为 register

#### static
- **修饰变量**：
  - 在函数内：静态局部变量，只初始化一次，生命周期为整个程序
  - 在函数外：静态全局变量，作用域仅限于本文件
- **修饰函数**：静态函数，作用域仅限于本文件

#### extern
- 声明变量或函数在其他文件中定义
- 用于跨文件访问全局变量和函数
- **与 static 的区别**：
  - static 修饰的全局变量/函数作用域仅限于本文件
  - extern 声明的全局变量/函数可以在其他文件中访问

### 1.2 sizeof 关键字
- 不是函数，是单目运算符
- 计算数据类型或变量所占内存大小（字节数）
- **重要特性**：
  - sizeof 在编译时求值，不是运行时
  - sizeof 可以计算数组大小：`sizeof(arr) / sizeof(arr[0])`
  - 对指针使用 sizeof 得到的是指针本身大小（4字节或8字节）
  - 对数组名使用 sizeof 得到的是整个数组大小

### 1.3 复合类型关键字

#### struct/union/enum
- **struct**：结构体，各成员有独立内存空间
- **union**：联合体，所有成员共享同一内存空间
- **enum**：枚举，定义一组命名的整数常量

#### typedef
- 为已有类型创建别名，不是创建新类型
- 提高代码可读性和可移植性
- 与 #define 的区别：typedef 有类型检查，#define 是文本替换

### 1.4 变量命名规则

**【规则 1-1】** 命名应当直观且可以拼读，可望文知意，便于记忆和阅读。标识符最好采用英文单词或其组合，不允许使用拼音。

**【规则 1-2】** 命名的长度应当符合 "min-length && max-information" 原则。标识符的长度一般不要过长，较长的单词可通过去掉"元音"形成缩写。英文词尽量不缩写，如果有缩写，在同一系统中对同一单词必须使用相同的表示法。

**【规则 1-3】** 当标识符由多个词组成时，每个词的第一个字母大写，其余全部小写。如 `int CurrentVal;`

**【规则 1-4】** 尽量避免名字中出现数字编号，如 Value1, Value2 等，除非逻辑上的确需要编号。

**【规则 1-5】** 对在多个文件之间共同使用的全局变量或函数要加范围限定符（建议使用模块名缩写作为范围限定符）。如 `GUI_`

**【规则 1-6】** 标识符名分为两部分：规范标识符前缀(后缀) + 含义标识。非全局变量可以不使用范围限定符前缀。

**【规则 1-7】** 作用域前缀命名规则：

| 标识符类型 | 作用域前缀 |
|-----------|-----------|
| Global Variable | g |
| File Static Variable | n |
| Function Static Variable | f |
| Auto Variable | a |
| Global Function | g |
| Static Function | n |

**【规则 1-8】** 数据类型前缀命名规则：

| Prefix | Data Type | Example |
|--------|-----------|---------|
| bt | bit | `Bit btVariable;` |
| b | boolean | `boolean bVariable;` |
| c | char | `char cVariable;` |
| i | int | `int iVariable;` |
| s | short[int] | `short sVariable;` |
| l | long[int] | `long lVariable;` |
| u | unsigned[int] | `unsigned uiVariable;` |
| d | double | `double dVariable;` |
| f | float | `float fVariable;` |
| p | pointer | `void *vpVariable;` |
| v | void | `void vVariable;` |
| st | enum/struct/union | `struct A stVariable;` |
| fp | function pointer | `void(*fpGetModeFuncList_a[])(void)` |
| _a | array of | `char cVariable_a[TABLE_MAX];` |
| _st | typedef struct/enum/union | `SM_EventOpt_st` |
| _pst | typedef struct/enum/union pointer | `SM_EventOpt_pst` |

**【规则 1-9】** 含义标识命名规则：
- 变量命名使用名词性词组：目标词 + 动词(过去分词) + [状语] + [目的地]
  - 如：`DataGotFromSD`
- 函数命名使用动词性词组：动词(一般现时) + 目标词 + [状语] + [目的地]
  - 如：`GetDataFromSD`

**【规则 1-10】** 程序中不得出现仅靠大小写区分的相似的标识符。特别注意数字 1 和小写字母 l、数字 0 和小写字母 o 之间的混淆。

**【规则 1-11】** 一个函数名禁止被用于其它之处。

**【规则 1-12】** 所有宏定义、枚举常数、只读变量全用大写字母命名，用下划线分割单词。

**【规则 1-13】** 局部变量中可采用通用的命名方式，仅限于 n、i、j 等作为循环变量使用。

**【规则 1-14】** 定义变量的同时千万千万别忘了初始化。定义变量时编译器并不一定清空了这块内存，它的值可能是无效的数据。

**【规则 1-15】** 不同类型数据之间的运算要注意精度扩展问题，一般低精度数据将向高精度数据扩展。

### 1.6 if/else 规则

**bool 变量与零值比较：**
- ✅ 正确：`if(bTestFlag); if(!bTestFlag);`
- ❌ 错误：`if(bTestFlag == 1); if(bTestFlag == TRUE);`

**float 变量与零值比较：**
- ✅ 正确：`if((fTestVal >= -EPSINON) && (fTestVal <= EPSINON));`
- ❌ 错误：`if(fTestVal == 0.0);`
- 不要在很大的浮点数和很小的浮点数之间进行运算

**指针变量与零值比较：**
- ✅ 正确：`if(NULL == p); if(NULL != p);`（推荐将 NULL 放左边防止误写为赋值）
- ❌ 错误：`if(p == 0); if(p);`

**【建议 1-16】** 程序中的分界符 `{` 和 `}` 应独占一行并对齐。缩进使用 4 个空格（不使用 Tab）。

**【规则 1-17】** 先处理正常情况，再处理异常情况。把正常情况的处理放在 if 后面，而不是 else 后面。

**【规则 1-18】** 确保 if 和 else 子句没有弄反。

**陷阱：if 语句后面的分号**
```c
if(NULL != p) ;  // 分号使 if 变成空语句
fun();           // 始终执行，不受 if 控制
```

**陷阱：else 悬垂问题**
```c
if(0 == x)
    if(0 == y) error();
else {
    // 这个 else 与内层 if 配对，而非外层！
}
```

### 1.7 switch/case 规则

**【规则 1-19】** 每个 case 语句的结尾绝对不要忘了加 break，否则将导致多个分支重叠（除非有意使多个分支重叠）。

**【规则 1-20】** 最后必须使用 default 分支。即使程序真的不需要 default 处理，也应该保留 `default: break;`

**【规则 1-21】** 按字母或数字顺序排列各条 case 语句。

**【规则 1-22】** 把正常情况放在前面，异常情况放在后面。

**【规则 1-23】** 按执行频率排列 case 语句，最常执行的放在前面。

**【规则 1-24】** 简化每种情况对应的操作。case 语句后面的代码尽量不要超过 20 行，超过则提取为子函数。

**【规则 1-25】** 不要为了使用 case 语句而刻意制造一个变量。

**【规则 1-26】** 把 default 子句只用于检查真正的默认情况，不要把最后一种情况用 default 处理。

**陷阱：case 后面只能是整型或字符型的常量或常量表达式。**

### 1.8 循环语句规则

**【建议 1-27】** 在多重循环中，如果有可能，应当将最长的循环放在最内层，最短的循环放在最外层，以减少 CPU 跨切循环层的次数。

**【建议 1-28】** for 语句的循环控制变量的取值采用"半开半闭区间"写法：`for(n=0; n<10; n++)` 而非 `for(n=0; n<=9; n++)`

**【规则 1-29】** 不能在 for 循环体内修改循环变量，防止循环失控。

**【规则 1-30】** 循环要尽可能的短，一般不超过 20 行。超过一屏的循环应提取子函数。

**【规则 1-31】** 把循环嵌套控制在 3 层以内。超过 3 层应重新设计。

### 1.9 goto 规则

**【规则 1-32】** 禁用 goto 语句。goto 可能跳过变量的初始化、重要的计算等语句。

### 1.10 void/return 规则

**【规则 1-33】** 如果函数没有返回值，那么应声明为 void 类型。

**【规则 1-34】** 如果函数无参数，那么应声明其参数为 void。如 `int function(void)`

**【规则 1-35】** 千万小心使用 void 指针类型。不能对 void 指针进行算法操作（ANSI 标准）。可移植写法：`(char *)pvoid++;`

**【规则 1-36】** 如果函数的参数可以是任意类型指针，那么应声明其参数为 `void *`。如 memcpy 和 memset 的原型。

**【规则 1-37】** void 不能代表一个真实的变量。`void a;` 是错误的。

**【规则 1-38】** return 语句不可返回指向"栈内存"的"指针"，因为该内存在函数体结束时被自动销毁。

### 1.11 const 规则

- const 修饰的是只读变量，不是常量
- const 推出的初始目的是为了取代预编译指令 `#define`
- const 修饰的只读变量必须在定义的同时初始化
- const 修饰指针的记忆法：先忽略类型名，const 离谁近就修饰谁
  ```c
  const int *p;       // *p 不可变，p 可变
  int const *p;       // *p 不可变，p 可变
  int *const p;       // p 不可变，*p 可变
  const int *const p; // 都不可变
  ```
- const 修饰函数参数防止意外修改：`void Fun(const int i);`
- const 修饰函数返回值：`const int Fun(void);`

### 1.12 volatile 关键字

- volatile 告诉编译器变量可能被编译器未知的因素更改（操作系统、硬件、其他线程）
- volatile 修饰的变量每次使用都必须从内存中重新读取
- 适用场景：寄存器变量、端口数据、多线程共享数据
- 注意：Debug 模式可能看不出来，需在 Release 模式测试

## 第二章 符号与注释规则

### 注释规则

**【规则 2-1】** 注释应当准确、易懂，防止有二义性。错误的注释不但无益反而有害。

**【规则 2-2】** 边写代码边注释，修改代码同时修改相应的注释。不再有用的注释要及时删除。

**【规则 2-3】** 注释是对代码的"提示"，而不是文档。程序中的注释应当简单明了。

**【规则 2-4】** 一目了然的语句不加注释。如 `i++; /* i加1 */` 是多余注释。

**【规则 2-5】** 对于全局数据（全局变量、常量定义等）必须要加注释。

**【规则 2-6】** 注释采用英文，尽量避免在注释中使用缩写。

**【规则 2-7】** 注释的位置应与被描述的代码相邻，可以与语句在同一行，也可以在上行，但不可放在下方。

**【规则 2-8】** 当代码比较长，特别是有多重嵌套时，应当在一些段落的结束处加注释。

**【规则 2-9】** 注释的缩进要与代码的缩进一致。

**【规则 2-10】** 注释代码段时应注重"为何做（why）"，而不是"怎么做（how）"。

**【规则 2-11】** 数值的单位一定要注释。

**【规则 2-12】** 对变量的范围给出注释。

**【规则 2-13】** 对一系列的数字编号给出注释。对于函数的入口出口数据给出注释。

### 运算符陷阱

**陷阱：逻辑运算符短路求值**
```c
int i=0, j=0;
if((++i>0) || (++j>0)) { } // 结果：i=1, j=0（短路求值）
```

**陷阱：位运算优先级**
```c
0x01<<2+3;  // 结果为 32，不是 7！因为 + 优先级高于 <<
```

**陷阱：移位溢出**
- 左移和右移的位数不能大于数据的长度，不能小于 0

**陷阱：++/-- 操作符**
- `(++i)+(++i)+(++i)` 的值在不同编译器下不同（未定义行为）
- 后缀运算在本计算单位计算结束之后再自加或自减
- 贪心法：编译器从左到右读入字符，每个符号包含尽可能多的字符

**陷阱：有符号右移**
- 对于有符号数，右移时符号位随同移动
- 负数右移时最高位补 0 或 1 取决于编译系统

**容易出错的优先级问题：**

| 表达式 | 经常误认为 | 实际结果 |
|--------|-----------|---------|
| `*p.f` | `(*p).f` | `*(p.f)` |
| `int *ap[]` | `int (*ap)[]` | `int *(ap[])`（指针数组） |
| `int *fp()` | `int (*fp)()` | `int *(fp())`（返回指针的函数） |
| `val & mask != 0` | `(val & mask) != 0` | `val & (mask != 0)` |
| `c = getchar() != EOF` | `(c = getchar()) != EOF` | `c = (getchar() != EOF)` |
| `msb << 4 + lsb` | `(msb << 4) + lsb` | `msb << (4 + lsb)` |
| `i = 1,2` | `i = (1,2)` | `(i = 1),2` |

## 第三章 预处理规则

### 宏定义规则

- 代码中一定不要出现"魔鬼数"，必须用宏或 const 变量代替
- 定义宏常数时建议用 const 代替 #define（有类型检查）
- 宏函数定义时参数必须加括号，整个表达式也要加括号：
  ```c
  // 错误
  #define SQR(x) x * x
  // 正确
  #define SQR(x) ((x)*(x))
  ```
- 宏定义中 SUM 后面的空格问题：`#define SUM (x) (x)+(x)` 定义的是宏 SUM 而非宏函数 SUM(x)
- 注释先于预处理指令被处理，不能用宏定义注释符号
- #undef 用来撤销宏定义

### 条件编译

- `#ifdef` / `#ifndef` / `#if` / `#elif` / `#else` / `#endif`
- 用于移植和调试
- **预定义宏**：
  - `__FILE__`：当前源文件名
  - `__LINE__`：当前行号
  - `__DATE__`：编译日期
  - `__TIME__`：编译时间
  - `__STDC__`：编译器是否符合 ANSI C 标准
  - `__cplusplus`：C++ 编译器定义

### 文件包含

- `<filename>` — 系统路径搜索
- `"filename"` — 当前目录优先搜索
- `#include` 是将已存在文件的内容嵌入到当前文件中
- **注意**：Windows 系统路径使用双反斜杠 `\\`，Unix/Linux 使用单斜杠 `/`
- 推荐使用相对路径提高可移植性

### 内存对齐

- 缺省情况下编译器默认将结构、栈中的成员数据进行内存对齐
- 访问未对齐的内存需要两次总线周期，对齐的只需一次
- 结构体成员排列技巧：将成员按从小到大排列可减少空洞
- `#pragma pack(n)` 改变对齐方式
- 对齐规则：每个成员按 `min(n, sizeof(item))` 对齐

## 第四章 指针和数组陷阱

### 核心概念

- 指针变量里存储的任何数据都将被当作地址来处理
- 32 位系统下不管什么指针类型，大小都为 4 字节
- `int *p = NULL;` — p 的值为 0（初始化）
- `*p = NULL;` — p 指向的内存赋值为 0（可能非法访问）

### 指针与数组的关键区别

- 数组名作为右值时代表首元素地址，但 `&a` 是整个数组的地址
- 定义为数组、声明为指针（或反之）会导致严重错误
- 无法向函数传递一个数组（退化为指针）
- 无法把指针变量本身传递给一个函数（传值调用）

### 陷阱清单

- `a` 和 `&a` 的区别：`a` 是首元素地址，`&a` 是整个数组的地址，类型不同
- `sizeof(数组)` 在函数内部变为 `sizeof(指针)`
- 二维数组参数与二维指针参数不匹配
- `int *ap[]` 是指针数组，`int (*pa)[]` 是数组指针

### 函数指针

- 函数指针定义：`int (*fp)(int, int);`
- `(*(void(*)())0)()` — 调用地址 0 处的函数
- 函数指针数组：`int (*fpArray[])(int, int);`

## 第五章 内存管理规则

### 野指针防护

- 定义指针变量的同时最好初始化为 NULL
- 用完指针之后也将指针变量的值设置为 NULL
- 除使用时外，别的时间都把指针"栓"到 NULL 地址处

### 栈、堆和静态区

- **静态区**：保存自动全局变量和 static 变量，整个程序生命周期存在
- **栈**：保存局部变量，函数范围内存在，效率高但空间有限
- **堆**：由 malloc/new 分配，由 free/delete 决定生命周期，灵活但容易出错

### 常见内存错误及对策

**错误1：指针没有指向一块合法的内存**
- 结构体成员指针未初始化 — 必须为每个指针成员 malloc 空间
- 没有为结构体指针分配足够的内存 — `sizeof(struct student)` vs `sizeof(struct student*)`
- 函数入口校验 — 使用 `assert(NULL != p)` 做参数校验

**错误2：为指针分配的内存太小**
- 字符串拷贝时忘了 `\0` 结束符：`malloc(strlen(p1)+1)`

**错误3：内存分配成功，但并未初始化**
- 定义变量时第一件事就是初始化
- 可初始化为 0 或 NULL
- 数组：`int a[10] = {0};` 或 `memset(a, 0, sizeof(a));`

**错误4：内存越界**
- 循环变量使用半开半闭区间，从 0 开始
- 注意 "多 1" 或 "少 1" 错误

**错误5：内存泄漏**
- malloc 的使用次数一定要和 free 相等
- malloc 两次只 free 一次会内存泄漏
- malloc 一次 free 两次肯定会出错

**错误6：内存释放后继续使用**
- `free(p)` 后必须 `p = NULL;`
- 函数不能返回指向栈内存的指针
- 复杂的内存使用应重新设计程序

### malloc 使用要点

1. 内存分配给谁？
2. 分配多大内存？
3. 是否还有足够内存分配？（必须检查返回值是否为 NULL）
4. 内存将用来存储什么格式的数据？
5. 分配好的内存在哪里？

- `malloc(0)` 不返回 NULL，但无法使用这块内存
- `free(p)` 只做一件事：斩断指针变量与这块内存的关系
- free 后指针变量保存的地址并没有改变，但已无所有权

## 第六章 函数设计规则

### 编码风格规则

**【规则 6-1】** 每一个函数都必须有注释。头部说明包含：
- Function Name、Create Date、Author/Corporation
- Description（功能描述）
- Param（参数说明）
- Return Code（返回值说明）
- Global Variable、File Static Variable、Function Static Variable
- Revision History（修改记录）

**【规则 6-2】** 每个函数定义结束之后以及每个文件结束之后都要加一个或若干个空行。

**【规则 6-3】** 在一个函数体内，变量定义与函数语句之间要加空行。

**【规则 6-4】** 逻辑上密切相关的语句之间不加空行，其它地方应加空行分隔。

**【规则 6-5】** 复杂函数中，在分支语句、循环语句结束之后需要适当的注释，方便区分各分支或循环体。

**【规则 6-6】** 修改别人代码时不要轻易删除，应该用适当的注释方式标记删除和新增。

**【规则 6-7】** 用缩行显示程序结构，缩进量统一使用 4 个字符（不使用 TAB 缩进）。

**【规则 6-8】** 在函数体的开始、结构/联合的定义、枚举的定义以及循环、判断等语句中的代码都要采用缩行。

**【规则 6-9】** 同层次的代码在同层次的缩进层上。

**【规则 6-10】** 代码行最大长度宜控制在 80 个字符以内。

**【规则 6-11】** 长表达式要在低优先级操作符处划分新行，操作符放在新行之首。

**【规则 6-12】** 如果函数中的参数较长，则要进行适当的划分。

**【规则 6-13】** 用正确的反义词组命名具有互斥意义的变量或相反动作的函数。如 `Set_Value/Get_Value`、`MinValue/MaxValue`。

**【规则 6-14】** 如果代码行中的运算符比较多，用括号确定表达式的操作顺序，避免使用默认的优先级。

**【规则 6-15】** 不要编写太复杂的复合表达式。

**【规则 6-16】** 不要有多用途的复合表达式。如 `d = (a = b + c) + r;` 应拆分为两个独立语句。

**【建议 6-17】** 尽量避免含有否定运算的条件表达式。`if(!(num >= 10))` 应改为 `if(num < 10)`

**【规则 6-18】** 参数的书写要完整，不要贪图省事只写参数的类型而省略参数名字。如果函数没有参数，则用 void 填充。

### 函数设计一般原则

**【规则 6-19】** 尽量少使用全局变量。各源文件负责本身文件的全局变量，同时提供一对对外函数：`niSet_ValueName()` 和 `niGet_ValueName()`。多线程编程时必须对读写操作加锁。

**【规则 6-20】** 参数命名要恰当，顺序要合理。目的参数放在前面，源参数放在后面。

**【规则 6-21】** 如果参数是指针，且仅作输入参数用，则应在类型前加 const。如 `void str_copy(char *strDestination, const char *strSource);`

**【规则 6-22】** 不要省略返回值的类型。如果函数没有返回值，应声明为 void 类型。

**【规则 6-23】** 在函数体的"入口处"，对参数的有效性进行检查。尤其是指针参数，尽量使用 assert 宏做入口校验，而不使用 if 语句校验。

**【规则 6-24】** return 语句不可返回指向"栈内存"的"指针"。

**【规则 6-25】** 函数的功能要单一，不要设计多用途的函数。

**【规则 6-26】** 函数体的规模要小，尽量控制在 80 行代码之内。

**【建议 6-27】** 相同的输入应当产生相同的输出。尽量避免函数带有"记忆"功能（少用 static 局部变量）。

**【建议 6-28】** 避免函数有太多的参数，参数个数尽量控制在 4 个或 4 个以内。

**【建议 6-29】** 尽量不要使用类型和数目不确定的参数（如 printf 风格）。

**【建议 6-30】** 有时候函数不需要返回值，但为了增加灵活性如支持链式表达，可以附加返回值。

**【建议 6-31】** 不仅要检查输入参数的有效性，还要检查通过其它途径进入函数体内的变量的有效性，例如全局变量、文件句柄等。

**【规则 6-32】** 函数名与返回值类型在语义上不可冲突。如 `getchar()` 返回 int 而非 char。

### 递归注意事项

- 递归效率很低，函数调用开销比循环大得多
- 递归深度太大会导致栈溢出
- 递归的停止条件一定要正确
- 不到万不得已不要用递归

## 第七章 文件结构规则

**【规则 7-1】** 每个头文件和源文件的头部必须包含文件头部说明和修改记录。包含内容：
- File Name、Copyright、Module Name
- CPU、RTOS（平台信息）
- Create Date、Author/Corporation
- Abstract Description
- Revision History

**【规则 7-2】** 头文件各部分的书写顺序：
1. Header File Header Section
2. Multi-Include-Prevent Section（`#ifndef`/`#define`/`#endif`）
3. Debug Switch Section
4. Include File Section
5. Macro Define Section
6. Structure Define Section
7. Prototype Declare Section

**【规则 7-3】** 源文件各部分的书写顺序：
1. Source File Header Section
2. Debug Switch Section
3. Include File Section
4. Macro Define Section
5. Structure Define Section
6. Prototype Declare Section
7. Global Variable Declare Section
8. File Static Variable Define Section
9. Function Define Section

**【规则 7-4】** 需要对外公开的常量放在头文件中，不需要对外公开的常量放在定义文件的头部。

**【规则 7-5】** 文件标识符分为两部分：文件名前缀和后缀。文件名前缀的最前面要使用范围限定符——模块名缩写。

**【规则 7-6】** 采用小写字母命名文件，避免使用通俗的文件名如 `public.c`。

## 开发经验（最佳实践）

### 1. 指针安全
```c
int *p = NULL;         // 定义即初始化为 NULL
p = (int *)malloc(sizeof(int) * n);
if(NULL == p) {         // malloc 后必须检查
    return ERROR;
}
// ... 使用 p ...
free(p);
p = NULL;               // free 后必须置 NULL
```

### 2. 函数入口校验
```c
void func(int *p) {
    assert(NULL != p);  // 使用 assert 做入口校验
    // ... 函数体 ...
}
```

### 3. 结构体压缩参数
当函数参数超过 4 个时，用结构体打包参数：
```c
typedef struct {
    int width;
    int height;
    int color;
    int style;
} DrawParams;

void draw(DrawParams *params);
```

### 4. 全局变量访问
```c
static int g_status;
int GetStatus(void) { return g_status; }
void SetStatus(int status) { g_status = status; }
```

### 5. 柔性数组（C99）
```c
typedef struct {
    int len;
    int data[];    // 柔性数组成员
} FlexArray;

FlexArray *fa = malloc(sizeof(FlexArray) + n * sizeof(int));
fa->len = n;
```

### 6. 大小端检测
```c
int checkSystem(void) {
    union check { int i; char ch; } c;
    c.i = 1;
    return (c.ch == 1);  // 1=小端, 0=大端
}
```

### 7. 安全的头文件保护
```c
#ifndef __MODULE_FILENAME_H
#define __MODULE_FILENAME_H
// ... 内容 ...
#endif
```

### 8. 内存对齐优化
```c
struct Bad {     // sizeof = 12 (编译器对齐填充)
    char c1;
    short s;
    char c2;
    int i;
};

struct Good {    // sizeof = 8 (无填充)
    char c1;
    char c2;
    short s;
    int i;
};
```

## 开发教训（常见陷阱）

### 1. 结构体成员指针未初始化
```c
struct student { char *name; int score; } stu;
strcpy(stu.name, "Jimy");  // 崩溃！name 未分配内存
```

### 2. malloc 大小错误
```c
pstu = malloc(sizeof(struct student*));  // 错误！应该是 sizeof(struct student)
```

### 3. 字符串拷贝遗漏结束符
```c
char *p2 = malloc(strlen(p1));           // 错误！缺少 +1
char *p2 = malloc(strlen(p1) + 1);       // 正确
```

### 4. malloc(0) 陷阱
```c
char *p = malloc(0);
if(NULL != p) { ... }  // 校验通过但无法使用
```

### 5. 野指针/悬垂指针
```c
char *p = malloc(100);
free(p);
// p 成为野指针！
if(NULL != p) {          // 校验无效！
    strcpy(p, "world");  // 未定义行为！
}
```

### 6. 返回栈内存指针
```c
char *Func(void) {
    char str[30];
    return str;  // 错误！str 在函数结束时被销毁
}
```

### 7. 有符号数溢出
```c
char a[1000];
for(int i=0; i<1000; i++) {
    a[i] = -1-i;  // char 溢出：-128~127 范围
}
strlen(a);  // 结果为 255 而非预期的 1000
```

### 8. 无符号数死循环
```c
unsigned int i;
for(i=9; i>=0; i--) {  // 死循环！unsigned 永远 >= 0
    printf("%u\n", i);
}
```

### 9. getchar 返回值截断
```c
char c = getchar();      // 错误！getchar 返回 int
if(EOF == c) { ... }     // EOF 可能被截断
// 正确：int c = getchar();
```

### 10. 注释嵌套陷阱
```c
/* 外层注释开始
/* 内层注释 */
外层注释结束 */  // 错误！C 注释不能嵌套
```

### 11. 反斜杠续行陷阱
```c
#define STR "hello \
world"  // 正确：反斜杠后不能有空格，下一行前也不能有空格

#define STR "hello \  // 错误：反斜杠后有空格
world"
```

### 12. 复合赋值表达式
```c
d = (a = b + c) + r;  // 开发教训：一个表达式做两件事
// 应拆分为：
a = b + c;
d = a + r;
```

### 11. 宏定义缺少括号
```c
#define SQR(x) x * x
SQR(10+1);  // 展开为 10+1*10+1 = 21，而非 121

// 正确：
#define SQR(x) ((x)*(x))
```

### 12. typedef vs #define 混淆
```c
#define PCHAR char*
PCHAR p3, p4;  // p4 是 char，不是 char*！

typedef char* pchar;
pchar p1, p2;  // p1 和 p2 都是 char*
```

### 13. 注释中的陷阱
```c
y = x/*p;  // 被解析为 y = x 加注释开始，而非除法！
// 正确：y = x / *p; 或 y = x / (*p);
```

### 14. for 循环修改循环变量
```c
for(n=0; n<10; n++) {
    n = 8;  // 开发教训：循环失控
}
```

### 15. 嵌套循环层次过深
```c
// 开发教训：超过 3 层嵌套
for(...) {
    for(...) {
        for(...) {
            for(...) {  // 应重构
```

### 16. switch case 遗漏 break
```c
switch(x) {
    case 1: doSomething();
    // 缺少 break！会穿透到 case 2
    case 2: doOther();
    break;
}
```

### 17. 复杂递归
```c
void fun(int i) {
    if(i>0) fun(i/2);
    printf("%d\n", i);
}
// 递归深度大时可能栈溢出，效率低
```
