# 嵌入式 Web 管理服务器 — 技术方案

> 目标：为宿主 C++ 后台应用提供嵌入式 Web 管理服务器，用于运维管理、状态监控、配置维护。
> Web 应用与宿主应用相互独立、松耦合，通过明确接口边界通信。

---

## 1. 需求与约束

| 维度 | 要求 |
|------|------|
| 语言标准 | C++11 |
| 浏览器兼容 | 主流浏览器，要求低（兼容老版浏览器） |
| 通信安全 | HTTPS + WSS（WebSocket Secure） |
| 通信方式 | WebSocket（实时双向） |
| 耦合度 | Web 应用与宿主应用松耦合、可独立演进 |
| 架构 | 简单、成熟、可靠、代码量小 |
| 三方库 | 轻量、主流、成熟、熟悉 |

---

## 2. 技术选型

### 2.1 候选库对比

| 库 | HTTP | HTTPS | WebSocket | 体量 | 成熟度 | C++11 | 备注 |
|----|:---:|:---:|:---:|------|:---:|:---:|------|
| **cpp-httplib** | ✅ | ✅ | 弱/实验 | 头文件 | 高 | ✅ | 静态文件 + HTTPS 开箱即用 |
| **websocketpp** | 基础 | ✅(TLS) | ✅ | 头文件 | 高 | ✅ | WS 专注，基于 Asio |
| Boost.Beast | ✅ | ✅ | ✅ | 重（依赖 Boost） | 高 | 需 C++14+ | 依赖 Boost，偏重 |
| civetweb | ✅ | ✅ | ✅ | 极小（单文件） | 高 | ✅ | C 风格回调 API，与 C++ 接口层风格不匹配 |
| Drogon | ✅ | ✅ | ✅ | 重 | 高 | 需 C++17 | 过重 |

### 2.2 选型结论

采用 **cpp-httplib + websocketpp 双库分工**，各司其职，均 header-only、C++ 开发者熟悉：

| 职责 | 库 | 说明 |
|------|-----|------|
| HTTPS + 静态文件托管 | **cpp-httplib** | header-only，`set_mount_point` 直接托管 web/ 目录，HTTPS 走 OpenSSL |
| WebSocket（WSS） | **websocketpp** | header-only，基于 Asio + OpenSSL，专注 WS，稳定成熟 |
| JSON | **RapidJSON** | 腾讯开源，高性能，header-only，C++11 |
| TLS | **OpenSSL** | 系统库，cpp-httplib 与 websocketpp 共用 |
| 异步底层 | **Asio (standalone)** | header-only，websocketpp 底层；用 standalone 版避免引入 Boost |

**为什么分两个库：** cpp-httplib 的 WebSocket 支持是实验性的不可靠，而 websocketpp 的 HTTP/静态文件能力很弱。两者恰好互补：cpp-httplib 管 HTTP(S) + 静态资源，websocketpp 专门跑 WebSocket。两个都是纯头文件，集成成本低。

> **已知代价（明确接受）**：双库 = 双端口 + 双 TLS 上下文 + 两套线程模型，是本方案最大的复杂度来源。相比单库方案——Boost.Beast 需 C++14+ 且引入 Boost，Drogon/civetweb 要么过重要么 C 风格回调——双 header-only 库在 C++11 约束下仍是代码量与依赖量最小的选择。接受该代价，不再为"简单"做额外辩护。

**端口分工：**
- `8443` (HTTPS) — cpp-httplib：托管 Web 应用静态资源 + 可选 REST 健康检查
- `8444` (WSS) — websocketpp：承载管理通信（JSON over WebSocket）

前端从 `https://host:8443` 加载页面，JS 内连 `wss://host:8444` 建立 WebSocket。浏览器对跨端口 WSS 兼容良好。

## 3. 系统架构

```
┌──────────────────────────────────────────────────────────┐
│                  浏览器 (Web 管理应用)                     │
│        HTML / CSS / JS  (静态资源，由服务器托管)           │
└────────────┬───────────────────────┬─────────────────────┘
             │ HTTPS (8443)          │ WSS (8444)
             │ 加载页面/静态资源      │ 管理通信
┌────────────▼───────────┐ ┌─────────▼──────────────────────┐
│  cpp-httplib (HTTPS)   │ │  websocketpp (WSS)             │
│  - 静态文件服务 web/    │ │  - WebSocket 端点              │
│  - (可选) REST 健康检查 │ │  - 承载 JSON 协议              │
└────────────┬───────────┘ └─────────┬──────────────────────┘
             │                        │
             └───────────┬────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│              管理桥接层 (Management Bridge)               │
│   - 协议解析 (JSON ↔ 方法调用)  (RapidJSON)               │
│   - 鉴权 / 会话                                           │
│   - 事件分发 (host → web 推送)                            │
└────────────────────────┬─────────────────────────────────┘
                         │  进程内接口调用 (IHostManagement)
                         │
┌────────────────────────▼─────────────────────────────────┐
│                  宿主 C++ 应用                            │
│  ┌──────────────────────────────────────────────────┐    │
│  │   IHostManagement  (抽象接口)                     │    │
│  └─────────────────────┬────────────────────────────┘    │
│                        │ 实现                             │
│  ┌─────────────────────▼────────────────────────────┐    │
│  │   宿主业务逻辑 / 配置 / 日志 / 指标               │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

### 分层说明
- **Web 层**：纯前端静态资源，可独立替换 / 升级，无需重编译宿主
- **服务器层**：cpp-httplib 提供 HTTPS + 静态托管，websocketpp 提供 WSS 双向通信
- **桥接层**：JSON 协议解析（RapidJSON）、鉴权、事件分发，桥接 WS 与宿主接口
- **接口层**：`IHostManagement` 抽象类，定义宿主暴露的管理能力边界
- **宿主层**：实现接口，自身业务逻辑不感知 Web / HTTP

### 线程模型

管理服务器运行在两个独立线程中，宿主主线程通过接口与之交互。

```
      宿主主线程 (业务循环)
           │
           │ IHostManagement* 注册
           ▼
┌──────────────────────┐
│   ManagementServer   │
│   主线程持有          │
└──────┬───────┬───────┘
       │       │
  ┌────▼──┐ ┌──▼──────────────────────┐
  │ 线程 A  │ 线程 B                    │
  │ cpp-httplib│ websocketpp + Asio     │
  │ 内置线程池  │ io_service.run()       │
  │ :8443      │ :8444                   │
  └───────────┘ └───────────────────────┘
```

| 线程 | 运行内容 | 说明 |
|------|----------|------|
| 宿主主线程 | 业务逻辑，持有 `IHostManagement` 实现 | 可能有自身线程池 |
| 线程 A（httplib 内部） | HTTPS 请求处理，回调在 httplib 线程池中执行 | 用户无感知 |
| 线程 B（Asio） | WebSocket I/O + `on_message` 回调 | 单线程事件循环 |

**线程安全契约：**

- `IHostManagement` 的方法会被**两个线程**调用，**实现者必须保证线程安全**：
  - 线程 A（httplib 线程池，多线程）：HTTPS 通道的 `login()`
  - 线程 B（Asio 事件循环，单线程）：WSS 通道的全部数据/调用接口（`getStatus`/`getMetrics`/`getConfig`/`setConfig`/`getLogs`/`reloadConfig`/`runDiagnostics`/`restart`）及 `validateToken()`
  - 跨线程并发：`login()`（线程 A）与 WSS 接口（线程 B）可能同时进入，**共享状态（如 token 会话表）必须加锁**
- **慢操作约定**：`runDiagnostics`、`restart` 等可能长时间阻塞的调用，宿主实现应内部投递到独立工作线程异步执行，**不得在调用线程上同步长占**——线程 B 被阻塞会卡死心跳与全部 WS I/O
- `EventCallback` 可能在宿主任意线程触发，桥接层内部加锁投递到线程 B 的写队列
- 桥接层用 `std::mutex` 保护 WS 连接列表与事件队列
- 推荐：`IHostManagement` 实现用 `std::mutex` 保护共享状态，或将请求投递到宿主线程队列单线程处理

### 双通道功能划分

两个通道职责明确分离：**HTTPS 负责资源加载与无状态查询，WSS 负责全部管理通信与实时推送**。

**HTTPS 通道（8443，cpp-httplib）— 资源与无状态查询**

| 路径 | 方法 | 作用 |
|------|------|------|
| `/`、`/app.js`、`/style.css` | GET | 托管 Web 应用静态资源 |
| `/api/health` | GET | 健康检查（供外部监控 / 负载均衡探活，无需建立 WS 长连接） |
| `/api/login` | POST | 登录认证（user / password → token） |

特点：短连接、无状态、可缓存、浏览器与外部工具均可直接访问。

**WSS 通道（8444，websocketpp）— 管理通信与实时推送**

承载第 4 节全部管理操作（数据接口 + 调用接口）：
- 实时推送：日志流、指标更新、状态变更、告警事件（server → web）
- 命令下发：restart、reloadConfig、runDiagnostics、setConfig（web → server）
- 增量查询：getLogs(sinceMs)、getMetrics

特点：长连接、有状态会话、双向、低延迟、统一鉴权与协议版本。

**划分原则**
- 静态资源 + 外部探活 → HTTPS：无状态、可缓存、外部可达，外部监控无需建立 WS
- 管理交互 + 实时推送 → WSS：有状态、长连接、双向，server push 仅 WS 能高效承载
- 前端流程：浏览器先 `https://host:8443` 加载页面 → 页面 JS 建立 `wss://host:8444` → 后续管理全部走 WSS

**为什么不合并到一个通道**
- websocketpp 的 HTTP / 静态文件能力弱，自写静态 handler 增加代码量；cpp-httplib 静态托管开箱即用（含缓存头、Range 等）
- 管理需实时推送，HTTP 轮询效率低；WS 长连接复用会话，避免反复握手
- 两个 header-only 库各管一摊，职责单一，符合"架构简单、代码量小"

## 4. 宿主接口设计

接口分三类：
- **认证接口**：登录校验，颁发会话令牌（token），走 HTTPS 通道
- **数据接口**：获取 / 设置状态、指标、配置、日志（只读或读写），走 WSS 通道
- **调用接口**：触发动作（重启、重载、诊断等），走 WSS 通道

### 4.1 抽象接口定义（C++11）

```cpp
// IHostManagement.h
#pragma once
#include <string>
#include <vector>
#include <functional>
#include <cstdint>

namespace mgmt {

struct HostStatus {
    std::string state;        // running / degraded / stopped
    uint64_t    uptimeMs;
    std::string version;
    int         pid;
};

struct Metric {
    std::string name;
    double      value;
    std::string unit;
};

struct ConfigItem {
    std::string key;
    std::string value;
    bool        readOnly;
};

struct LogEntry {
    uint64_t    timestampMs;
    std::string level;        // info / warn / error
    std::string message;
};

struct Event {                // 服务器推送事件
    std::string type;         // log / metric / state / alert
    std::string payloadJson;
};

class IHostManagement {
public:
    virtual ~IHostManagement() {}

    // ---- 数据接口 ----
    virtual HostStatus              getStatus() = 0;
    virtual std::vector<Metric>     getMetrics() = 0;
    virtual std::vector<ConfigItem> getConfig() = 0;
    virtual bool                    setConfig(const std::string& key,
                                              const std::string& value,
                                              std::string& err) = 0;
    virtual std::vector<LogEntry>   getLogs(uint64_t sinceMs,
                                            uint32_t limit) = 0;

    // ---- 调用接口 ----
    // restart: 异步操作，调用后宿主可能立即退出进程。
    //   宿主实现只负责"触发进程退出"，不负责推送事件或关闭连接——
    //   桥接层在调用本方法前已完成 accepted 响应、restart scheduled 事件推送与 WS 连接关闭。
    //   完整时序见 4.3 节。
    virtual bool restart(std::string& err) = 0;
    virtual bool reloadConfig(std::string& err) = 0;
    virtual bool runDiagnostics(std::string& resultJson,
                                std::string& err) = 0;

    // ---- 认证接口 ----
    // 成功返回 true，token 出参为会话令牌；失败 err 填原因
    virtual bool login(const std::string& user,
                       const std::string& password,
                       std::string& token,
                       std::string& err) = 0;

    // ---- 事件订阅（用于向 Web 端推送）----
    using EventCallback = std::function<void(const Event&)>;
    virtual void setEventListener(EventCallback cb) = 0;

    // ---- Token 校验（由桥接层在 WS 鉴权阶段调用）----
    // 校验 token 有效性，返回 true 并出参填充 session 信息
    struct SessionInfo {
        std::string user;
        std::string role;   // admin / viewer
    };
    virtual bool validateToken(const std::string& token,
                               SessionInfo& session,
                               std::string& err) = 0;
};

} // namespace mgmt
```

### 4.2 数据接口一览

| 接口 | 入参 | 出参 | 说明 |
|------|------|------|------|
| getStatus | — | HostStatus | 运行状态、版本、PID、运行时长 |
| getMetrics | — | Metric[] | 关键指标（CPU、内存、QPS 等） |
| getConfig | — | ConfigItem[] | 当前配置项 |
| setConfig | key, value | ok / err | 修改配置项（运行时生效，宿主负责持久化到文件） |
| getLogs | sinceMs, limit | LogEntry[] | 拉取日志（增量） |

### 4.3 调用接口一览

| 接口 | 入参 | 出参 | 说明 |
|------|------|------|------|
| restart | — | accepted / err | 重启宿主应用（异步，返回 accepted 后进程即将退出） |
| reloadConfig | — | ok / err | 重新加载配置 |
| runDiagnostics | — | resultJson / err | 执行诊断，返回结果 |

> `restart` 语义（统一流程，责任全部在桥接层，宿主只负责触发退出）：
> 1. 桥接层收到 `restart` 请求 → 回 `accepted` 响应（见 5.9）
> 2. 向该 WS 客户端推送 `"restart scheduled"` 事件
> 3. 主动关闭该 WS 连接
> 4. 调用 `IHostManagement::restart()`，宿主在其中触发进程退出
>
> 宿主实现**不应**在 `restart()` 中推送事件或发送响应（连接届时已关闭）。

### 4.4 认证接口一览

| 接口 | 入参 | 出参 | 通道 | 说明 |
|------|------|------|------|------|
| login | user, password | ok / token / err | HTTPS (`POST /api/login`) | 校验账号密码，成功颁发会话令牌 |

> login 走 HTTPS 而非 WSS：登录是建立会话的第一步，须先于 WebSocket。
>
> **WSS 鉴权采用"先连后验"模式：**
> 1. 浏览器用 token 建立 WSS 连接（`wss://host:8444`）
> 2. 首条消息携带 token：`{ "kind": "auth", "token": "..." }`
> 3. 桥接层调用 `IHostManagement::validateToken()` 校验
> 4. 校验失败 → 返回错误并关闭连接；校验成功 → 后续管理操作复用该会话
>
> **为什么不走 Header/Query 传 token：** 浏览器 `WebSocket` API 不支持在升级请求中设置自定义 HTTP Header；Query param 会暴露 token 到 URL（日志泄露风险）。因此采用先连后验，token 仅在加密的 WS 帧内传输。

## 5. 通信协议（WSS 通道）

> 以下协议运行在 WSS 通道（8444），承载全部管理通信。
> HTTPS 通道（8443）托管静态资源、健康检查与登录认证（`POST /api/login`），不承载管理协议。

WebSocket 消息统一使用 JSON 文本帧。

> **消息边界**：依赖 websocketpp 的 `max_message_size`（默认 1MB）限制单帧大小，防止恶意/异常大帧耗尽内存。嵌入式场景默认值足够；若需承载大体积诊断结果（如 `runDiagnostics`），应改为分片事件推送，而非放大单帧。

### 5.1 鉴权（Web → 宿主，WSS 连接建立后首条消息）

客户端声明 token 与期望协议版本：
```json
{
  "kind": "auth",
  "token": "xxx",
  "proto": "v1"
}
```

服务器校验通过后返回确认版本与会话信息：
```json
{
  "kind": "auth_ok",
  "proto": "v1",
  "supported": ["v1"],
  "session": { "user": "admin", "role": "admin" }
}
```

校验失败返回错误并关闭连接。后续所有请求/事件均复用该会话。

### 5.2 请求（Web → 宿主）

```json
{
  "id": "1",
  "proto": "v1",
  "kind": "request",
  "action": "getStatus",
  "params": {}
}
```

### 5.3 响应（宿主 → Web）

成功：
```json
{
  "id": "1",
  "proto": "v1",
  "kind": "response",
  "status": "ok",
  "data": { "state": "running", "uptimeMs": 123456, "version": "1.0.0", "pid": 4321 }
}
```

错误：
```json
{
  "id": "1",
  "proto": "v1",
  "kind": "response",
  "status": "error",
  "error": { "code": "PERM_DENIED", "message": "权限不足" }
}
```

### 5.4 事件（宿主 → Web 推送）

```json
{
  "proto": "v1",
  "kind": "event",
  "event": "log",
  "data": { "timestampMs": 1690000000000, "level": "warn", "message": "..." }
}
```

### 5.5 action 路由表

| action | 对应接口 | 类型 |
|--------|----------|------|
| getStatus | getStatus | 数据 |
| getMetrics | getMetrics | 数据 |
| getConfig | getConfig | 数据 |
| setConfig | setConfig | 数据 |
| getLogs | getLogs | 数据 |
| restart | restart | 调用 |
| reloadConfig | reloadConfig | 调用 |
| runDiagnostics | runDiagnostics | 调用 |

> 协议携带版本字段 `proto`，便于前后端独立演进。

### 5.6 心跳机制

WebSocket 连接可能因代理/NAT 超时静默断开，协议层定义心跳保活。

```json
{ "kind": "ping" }
```

服务器收到后立即回复：
```json
{ "kind": "pong" }
```

客户端每 30 秒发送一次 ping，连续 3 次无 pong 则认为连接断开，触发重连。

> 也可依赖 websocketpp 的 WebSocket 协议层 ping/pong 帧，但应用层心跳便于监控和调试。

### 5.7 事件订阅

客户端可声明订阅的事件类型，服务器仅推送已订阅类型，避免全量广播浪费带宽。

订阅（Web → 宿主）：
```json
{
  "id": "sub-1",
  "kind": "subscribe",
  "events": ["log", "state", "alert"]
}
```

退订：
```json
{
  "id": "sub-1",
  "kind": "unsubscribe",
  "events": ["metric"]
}
```

桥接层维护每个连接的事件过滤集，默认连接建立后不订阅任何事件，客户端必须显式订阅。

### 5.8 协议版本协商

客户端在 auth 阶段声明支持的版本：
```json
{ "kind": "auth", "token": "xxx", "proto": "v2" }
```

服务端在 `auth_ok` 中返回实际使用的版本及支持的版本列表：
```json
{
  "kind": "auth_ok",
  "proto": "v1",
  "supported": ["v1"]
}
```

客户端据此降级或提示升级。

> `auth` / `auth_ok` 的完整字段示例见 5.1；本节仅说明版本协商机制，不重复完整报文。

### 5.9 特殊响应状态

除 `ok` / `error` 外，异步操作（如 `restart`）返回 `accepted`：

```json
{
  "id": "1",
  "proto": "v1",
  "kind": "response",
  "status": "accepted",
  "data": { "message": "restart scheduled, connection will close" }
}
```

收到 `accepted` 后客户端应等待事件推送最终结果。

> `restart` 的完整时序（accepted 响应 → 事件推送 → 关闭连接 → 调用宿主）见 4.3 节。

## 6. 松耦合设计要点

1. **接口隔离**：宿主仅实现 `IHostManagement`，不依赖 cpp-httplib / websocketpp / HTTP / JSON
2. **依赖注入**：启动时宿主将 `IHostManagement*` 注册给管理服务器，服务器反向调用
3. **Web 资源独立**：前端为静态文件，可单独替换，无需重编译
4. **协议版本化**：`proto` 字段保证前后端独立演进
5. **编译解耦**：接口为头文件，宿主与管理服务器可分别编译、单独测试

## 7. 安全性

### 7.1 传输安全
- **HTTPS / WSS**：cpp-httplib 与 websocketpp 各自加载 OpenSSL 证书，强制 TLS
- **证书**：开发用自签名，生产用正式证书
- **证书热加载**：提供 `POST /api/reload-cert`（HTTPS）或 SIGHUP 信号支持，避免证书到期需要重启

### 7.2 认证与鉴权
- **登录**：浏览器 `POST /api/login`（HTTPS）提交账号密码 → 宿主 `login()` 校验 → 返回 token
- **WSS 鉴权**：采用"先连后验"模式（见 4.4 节），token 仅在加密 WS 帧内传输，不暴露到 URL 或 HTTP Header
- **会话模型（连接级）**：鉴权在连接建立时执行一次（见 4.4"先连后验"），成功后桥接层缓存会话，后续请求复用，**不再逐条调用 `validateToken()`**；桥接层跟踪 token 过期时间，过期时主动关闭连接（见 7.3）

### 7.3 Token 生命周期

| 属性 | 值 | 说明 |
|------|-----|------|
| 生成方式 | 随机字符串 (≥128bit) | 宿主 `login()` 生成的不可猜测令牌 |
| 有效期 | 可配置，默认 24 小时 | 过期后桥接层关闭 WS 连接 |
| 刷新 | 前端定时重新登录 | 简化设计，不引入 refresh token |
| 存储 | 宿主实现决定（内存/持久化） | 推荐内存存储，重启后需重新登录 |
| 撤销 | 宿主 logout() / session 管理 | 可选接口 |

### 7.4 权限控制
- 调用接口（restart 等）需更高权限，由桥接层根据 `session.role` 判断
- 事件广播根据连接会话的 role 过滤（admin 收全量，viewer 仅收状态/指标）

### 7.5 速率限制
桥接层对高危操作实施频率控制，**限速器在桥接层集中实现、线程安全**（`login` 来自 httplib 线程，`restart`/`setConfig` 来自 Asio 线程，共享同一计数器）：

| 操作 | 限制 | 说明 |
|------|------|------|
| restart | 1 次 / 60s | 防止频繁重启 |
| setConfig | 10 次 / s | 防止配置轰炸 |
| login | 5 次 / 30s | 防止暴力破解 |

### 7.6 来源校验
- 校验 `Origin` 头，防止 CSWSH（Cross-Site WebSocket Hijacking）
- 桥接层维护允许的 Origin 白名单，**必须可配置**（环境变量或配置文件）
- 默认值仅含本地地址（`localhost`、`127.0.0.1`）；**远程/局域网部署时必须显式加入实际访问域名或 IP**，否则合法管理访问会被拒

## 10. 关键流程

### 10.1 启动流程
```
宿主 main()
  ├─ 创建 HostApp (实现 IHostManagement)
  ├─ 创建 ManagementServer(host, httpsPort=8443, wssPort=8444, cert)
  ├─ server.start()
  │    ├─ 启动线程 B: io_service.run() (websocketpp WSS, :8444)
  │    └─ 启动线程 A: cpp-httplib 监听 :8443 (内部线程池)
  │         └─ 挂载 web/ 静态目录 + REST 健康检查
  ├─ 设置事件监听 → server 推送到 WS 客户端
  └─ 宿主业务循环 (server.start() 非阻塞)
```

### 10.2 请求处理流程（WSS 通道）
```
浏览器 wss://host:8444 发送 JSON 请求
  → websocketpp 回调 (on_message)
  → ManagementServer 解析 action (RapidJSON)
  → 查路由表 → 调用 IHostManagement 对应方法
  → 序列化结果为 JSON 响应
  → 回发浏览器
```

### 10.3 事件推送流程
```
宿主产生事件 → setEventListener 回调
  → ManagementServer 组装 event JSON
  → 根据连接订阅过滤集，仅向已订阅该类型的连接发送
```

### 10.4 优雅关闭流程
```
宿主 main()
  ├─ 收到 SIGTERM / 业务退出信号
  ├─ server.shutdown()
  │    ├─ 1. 向所有 WS 客户端发送 "server shutting down" 事件
  │    ├─ 2. 停止接受新的 WS 连接
  │    ├─ 3. 关闭所有现有 WS 连接
  │    ├─ 4. io_service.stop() → 线程 B 退出
  │    └─ 5. cpp-httplib.stop() → 线程池退出
  ├─ 清理宿主资源
  └─ exit
```

## 12. 前端错误处理与重连策略

前端 `app.js` 需覆盖以下场景：

**WS 断开重连：**
- 监听 `onclose` 事件，自动重连（指数退避：1s → 2s → 4s → ...，最大 30s）
- 重连后重新发送 `auth` 消息 + 恢复订阅
- 断连期间在 UI 显示"连接断开"提示

**请求超时：**
- 每个 request 维护 `id → timer` 映射，默认超时 10s 未收到响应则 reject
- 超时后 UI 提示操作失败

**restart 特殊处理：**
- 发送 `restart` 请求后，收到 `accepted` 响应即显示"重启中..."
- 监听 `onclose`，**不自动重连**（进程正在重启，旧 token 即将失效）
- 进程重启后需用户手动触发重新登录（旧会话不再有效）；可用 `/api/health`（HTTPS）轮询探测进程是否恢复上线，恢复后再引导重新登录

**network offline：**
- 浏览器 `navigator.onLine` 检测，离线时暂停重连，恢复后立即重试

## 13. 管理服务器日志

管理服务器自身需要日志输出，用于调试和排查问题。使用宿主应用的日志框架（通过 `IHostManagement` 扩展或独立 logger 配置）。

| 级别 | 场景 | 示例 |
|------|------|------|
| INFO | 服务器启动/停止、WS 连接建立/断开 | "WS server started on :8444" |
| WARN | 鉴权失败、协议错误、速率限制触发 | "auth failed: invalid token" |
| ERROR | TLS 证书加载失败、端口绑定失败 | "bind :8443 failed (EACCES)" |
| DEBUG | 每一条 WS 消息的 action 和大小 | "req id=3 action=getStatus (54B)" |

**实现方式：** 桥接层提供 `setLogger(std::function<void(int level, const char* msg)>)` 接口，由宿主注入。生产环境默认 INFO，开发环境可调至 DEBUG。

## 14. 测试策略

管理服务器提供 mock `IHostManagement` 实现的测试宿主，支持自动化测试。

| 测试类型 | 内容 | 工具 |
|----------|------|------|
| 单元测试 | JsonCodec 序列化/反序列化、Protocol 路由表、鉴权逻辑 | Catch2 或自带 assert |
| 集成测试 | Mock 宿主 + 真实 websocketpp/cpp-httplib → WebSocket 客户端发起请求验证 | 自写 Python/Node 脚本 |
| 端到端测试 | 完整启动 + 浏览器自动化 | 可选，非必须 |

**Mock 宿主要求：**
- 可配置的返回值（status/metrics 等返回预设数据）
- 可检查调用的方法及参数（验证 restart 是否被调用）
- 支持脚本触发事件推送（验证 WS 客户端是否收到事件）
